# Feature Spec: 일일 자원·방문자 조회 최적화

## Source

- PRD: `specs/031-daily-resource-visitor-query-optimization/prd.md`
- Principles: `specs/principles.md`

## User Scenarios

### Scenario 1: 오전 6시 날짜 전환

- Given 오전 5시 59분에 전날 위치가 캐시되어 있다.
- When 서울 시간이 오전 6시가 된다.
- Then 이후 응답은 오늘 날짜를 조회하고 전날 캐시를 재사용하지 않는다.

### Scenario 2: 과거 위치 자동 정리

- Given DB에 과거·오늘·미래 위치가 함께 있다.
- When 오전 6시 정기 정리 또는 애플리케이션의 안전 정리가 실행된다.
- Then 과거 위치만 물리 삭제되고 오늘과 미래 예약은 유지된다.

### Scenario 3: 반복 위치 조회

- Given 같은 게임 날짜의 현재 위치가 한 번 조회되었다.
- When 여러 페이지나 탭 복귀에서 현재 위치 API를 다시 호출한다.
- Then 위치 DB 조회는 반복하지 않으며 각 응답의 서버 시각은 실제 호출 시각을 반영한다.

### Scenario 4: 관리자 변경 반영

- Given 현재 날짜 위치가 캐시되어 있다.
- When 관리자가 위치를 저장하거나 삭제한다.
- Then 다음 API 호출은 캐시가 아닌 DB에서 최신 상태를 읽는다.

### Scenario 5: HTML 페이지 조회수 표시

- Given 사용자가 일반 위키 화면을 요청한다.
- When 전역 화면 속성을 구성한다.
- Then 세션 최초 방문이면 방문자 수를 한 번 증가시키고, 오늘·주간 합계를 단일 집계 호출로 화면에 제공한다.

### Scenario 6: JSON API 호출

- Given 헤더 또는 화면 스크립트가 JSON API를 호출한다.
- When 전역 Advice가 요청을 처리한다.
- Then 방문자 세션을 만들거나 방문자 증가·집계 SQL을 실행하지 않는다.

## Functional Requirements

- FR-001: 시스템은 서울 시간 오전 6시를 게임 날짜 경계로 사용해야 한다.
- FR-002: 시스템은 현재 게임 날짜보다 이른 `daily_resource_locations` 행을 삭제할 수 있어야 한다.
- FR-003: 시스템은 매일 오전 6시 과거 위치 정리를 실행해야 한다.
- FR-004: 시스템은 정기 실행 누락에 대비해 날짜별 한 번의 안전 정리를 수행해야 한다.
- FR-005: 시스템은 현재 날짜의 위치 조회 결과를 게임 날짜 단위로 캐시해야 한다.
- FR-006: 시스템은 위치 응답의 `serverTime`을 캐시하지 않아야 한다.
- FR-007: 시스템은 위치 저장·삭제 성공 후 캐시를 무효화해야 한다.
- FR-008: 시스템은 `/api/**`, `/wiki/map/api/**`, `@ResponseBody`, `@RestController` 요청을 방문자 추적 및 푸터 집계에서 제외해야 한다.
- FR-009: 시스템은 오늘 방문자 수와 최근 7일 방문자 수를 한 번의 매퍼 호출로 조회해야 한다.
- FR-010: 시스템은 기존 푸터 모델 속성명과 현재 위치 API 응답 형식을 유지해야 한다.

## Non-Functional Requirements

- NFR-001: 동일 게임 날짜의 위치 API N회 호출에서 위치 SELECT는 1회여야 한다.
- NFR-002: 일반 화면 한 요청에서 방문자 합계 SELECT는 1회여야 한다.
- NFR-003: JSON API 요청에서 방문자 서비스 호출은 0회여야 한다.
- NFR-004: 캐시와 정리 상태는 동시 요청에서도 잘못된 날짜 값을 반환하지 않아야 한다.
- NFR-005: 신규 외부 의존성이나 DB 스키마 변경 없이 구현해야 한다.

## Edge Cases

- 05:59:59와 06:00:00 사이에서 게임 날짜가 바뀌면 날짜 키 불일치로 기존 캐시는 자동 폐기한다.
- 현재 날짜의 DB 행이 없는 빈 상태도 캐시하여 반복적인 미존재 조회를 막는다.
- 관리자가 미래 예약을 저장해도 현재 캐시는 안전하게 무효화하고, 미래 행은 정리하지 않는다.
- 삭제 대상이 없어도 정리 작업은 정상 완료되어야 한다.
- 루트 `/api`처럼 슬래시가 없는 경로와 하위 `/api/...`를 모두 API로 판별하고, 경로명이 다른 JSON 핸들러는 응답 어노테이션으로 판별한다.
- 정적 리소스는 MVC 컨트롤러 Advice 대상이 아니며 별도 처리하지 않는다.

## Data Requirements

- `daily_resource_locations.game_date`의 기존 고유 인덱스를 사용한다.
- 과거 위치는 복구 목적 없이 물리 삭제한다.
- 오늘과 미래 위치는 보존한다.
- `visitor_stats`의 기존 날짜별 집계 행을 사용하며 저장 형식은 변경하지 않는다.

## Clarifications

- Q: 오전 6시에 사용자 화면만 전환하면 되는가, DB의 과거 행도 삭제하는가?
  A: 사용자 요청과 승인된 범위에 따라 과거 행도 삭제한다. 다만 오늘과 미래 예약은 유지한다.
- Q: 위치 API 응답 전체를 캐시하는가?
  A: 아니다. 위치 데이터만 캐시하고 클라이언트 타이머 정확성을 위해 서버 시각은 매 호출마다 생성한다.
- Q: 조회수에 짧은 TTL 캐시도 적용하는가?
  A: 이번에는 API 제외와 단일 SQL로 중복 왕복을 제거한다. 정확한 실시간 숫자를 유지하기 위해 조회수 TTL 캐시는 적용하지 않는다.
