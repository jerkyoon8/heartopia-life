# PRD: 일일 자원·방문자 조회 최적화

## 1. Summary

### Problem

형광석·참나무의 지난 날짜 데이터가 관리자 목록과 DB에 계속 남고, 현재 위치 API는 페이지 이동과 탭 복귀마다 동일한 날짜를 다시 조회한다. 오늘·주간 방문자 수는 HTML뿐 아니라 JSON API 요청에서도 각각 별도 SQL로 조회되어 한 페이지 로드에서 불필요한 DB 왕복이 반복된다.

### Proposed Solution

오전 6시를 게임 날짜 경계로 유지하면서 과거 위치 행을 정리하고 현재 날짜 위치 조회만 서버 메모리에 캐시한다. 방문자 전역 모델 처리는 화면 요청에만 적용하고 오늘·주간 집계를 단일 SQL로 합친다.

### Success Criteria

- 오전 6시부터 전날 위치가 반환되지 않고, 과거 행은 제거되며 오늘과 미래 예약은 보존된다.
- 같은 게임 날짜의 반복 위치 API 호출은 DB를 한 번만 조회하고 응답의 서버 시각은 호출 시점마다 최신이다.
- 관리자 저장·삭제 후에는 캐시가 즉시 무효화되어 다음 조회에 최신 값이 반영된다.
- `/api/**`, `/wiki/map/api/**` 및 그 밖의 JSON 응답 요청은 방문자 증가와 오늘·주간 조회를 수행하지 않는다.
- HTML 요청의 오늘·주간 조회는 SQL 한 번으로 완료된다.

## 2. Users And Use Cases

### Primary Users

- 헤더에서 오늘의 형광석·참나무 위치를 확인하는 방문자
- 날짜별 자원 위치를 미리 등록하는 관리자
- 푸터에서 오늘·주간 방문자 수를 확인하는 운영자와 방문자

### User Stories

- As a 방문자, I want to 오전 6시 이후 이전 위치가 보이지 않길 원한다, so that 현재 게임 날짜의 정보만 신뢰할 수 있다.
- As a 관리자, I want to 미래 예약은 유지하면서 지난 기록은 자동 정리되길 원한다, so that 관리 목록이 불필요하게 길어지지 않는다.
- As a 운영자, I want to 조회수 표시가 적은 DB 요청으로 계산되길 원한다, so that 공통 헤더 API가 늘어나도 DB 부하가 불필요하게 증가하지 않는다.

## 3. Functional Scope

### In Scope

- 현재 게임 날짜보다 과거인 일일 자원 행의 물리 삭제
- 오전 6시 정기 정리와 시작/최초 사용 시 안전 정리
- 현재 게임 날짜의 위치 DB 결과 캐시
- 관리자 저장·삭제 및 날짜 경계에서 캐시 무효화
- API 경로와 `@ResponseBody`/`@RestController` 요청을 전역 방문자 집계 대상에서 제외
- 오늘·최근 7일 방문자 수 단일 SQL/DTO 조회
- 서비스·전역 Advice·MyBatis 매퍼·템플릿 계약 회귀 테스트

### Out Of Scope

- 미래 예약 삭제
- 브라우저 장기 캐시 또는 CDN 캐시 도입
- Redis 등 외부 캐시 도입
- 방문자 집계 정의나 세션당 1회 증가 정책 변경
- 운영 서버 배포와 운영 DB 직접 정리

## 4. Acceptance Criteria

- 게임 날짜는 서울 시간 기준 `현재 시각 - 6시간`의 날짜로 계산한다.
- 정리 SQL은 `game_date < 현재 게임 날짜`만 삭제한다.
- 동일 게임 날짜 반복 조회는 캐시를 사용하지만 `serverTime`은 매 응답마다 현재 시각으로 생성한다.
- 05:59와 06:00 경계에서 서로 다른 날짜 캐시를 사용한다.
- 저장 또는 삭제 후 다음 현재 위치 조회는 DB를 다시 읽는다.
- API 또는 JSON 응답 요청은 세션에 `visited`를 쓰지 않고 방문자 서비스도 호출하지 않는다.
- 일반 HTML 요청은 세션당 한 번 방문자를 증가시키고 집계 조회를 한 번 호출한다.
- 오늘과 주간 값은 기존 템플릿 속성명 `todayVisitors`, `weeklyVisitors`를 유지한다.

## 5. Constraints

- Tech: Java 17, Spring Boot 3.4.2, MyBatis, MySQL 8.0, 단일 JVM 메모리 캐시.
- Time: 기존 화면·API 응답 형식은 변경하지 않는다.
- Data: 신규 테이블·컬럼·인덱스 없이 기존 테이블을 사용한다.
- External Dependencies: 추가하지 않는다.

## 6. Risks

- 캐시된 응답 시각이 오래되어 클라이언트의 오전 6시 타이머가 틀어질 수 있음: DB 위치만 캐시하고 응답 시각은 매번 새로 만든다.
- 정기 작업이 재시작 등으로 실행되지 않을 수 있음: 서비스 시작/최초 조회에서도 날짜별 한 번 정리하는 안전 경로를 둔다.
- API 판별 누락으로 조회수 SQL이 계속 실행될 수 있음: 주요 API 경로와 실제 Spring MVC `@ResponseBody` 디스패치를 함께 테스트한다.
- 다중 인스턴스에서 로컬 캐시가 잠시 다를 수 있음: 현재 운영은 한 인스턴스가 트래픽을 받으며 관리자 변경은 해당 인스턴스에서 처리된다. 외부 분산 캐시는 범위에서 제외한다.

## 7. Open Questions

- 없음. 사용자가 제안한 최적화 범위 전체와 충분한 회귀 테스트 진행을 승인했다.
