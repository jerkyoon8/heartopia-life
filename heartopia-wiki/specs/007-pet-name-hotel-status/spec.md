# Feature Spec: 반려동물 이름 수정 및 호텔 상태

## Source

- PRD: `specs/007-pet-name-hotel-status/prd.md`
- Principles: `specs/principles.md`

## User Scenarios

### Scenario 1: 이름 수정

- Given 사용자가 등록된 반려동물을 선택했다.
- When 이름 수정 UI에서 유효한 새 이름을 저장한다.
- Then 목록과 먹이 기록 제목에 새 이름이 즉시 반영되고 저장된다.

### Scenario 2: 호텔 입실

- Given 호텔 입실 반려동물이 5마리 미만이다.
- When 선택한 반려동물의 호텔 체크를 켠다.
- Then 해당 반려동물이 입실 상태로 저장되고 목록과 선택 영역에 호텔 표시가 나타난다.

### Scenario 3: 호텔 퇴실

- Given 선택한 반려동물이 호텔 입실 상태다.
- When 호텔 체크를 끈다.
- Then 입실 상태와 강조 표시가 제거되고 다른 반려동물을 체크할 수 있는 자리가 생긴다.

### Scenario 4: 호텔 정원 초과 방지

- Given 서로 다른 반려동물 5마리가 호텔 입실 상태다.
- When 여섯 번째 반려동물의 호텔 체크를 켠다.
- Then 상태는 변경되지 않고 최대 5마리라는 안내가 표시된다.

### Scenario 5: 기존 프로필 호환

- Given 저장된 반려동물 프로필에 호텔 필드가 없다.
- When 프로필을 불러온다.
- Then 해당 반려동물은 퇴실 상태로 정상 표시되고 다른 기록은 유지된다.

## Functional Requirements

- FR-001: 시스템은 선택한 반려동물의 이름 편집을 시작·저장·취소할 수 있어야 한다.
- FR-002: 이름 편집 입력에는 현재 이름이 기본값으로 들어가야 한다.
- FR-003: 이름은 공백 정리 후 1자 이상 80자 이하만 허용해야 한다.
- FR-004: 이름 저장 후 반려동물 ID, 종류, 먹이 기록 및 호텔 상태는 유지되어야 한다.
- FR-005: 각 프로필은 호텔 입실 여부를 불리언으로 저장해야 한다.
- FR-006: 사용자는 선택한 반려동물의 호텔 입실 여부를 토글할 수 있어야 한다.
- FR-007: 시스템은 전체 프로필 중 호텔 입실 상태를 최대 5개로 제한해야 한다.
- FR-008: 여섯 번째 입실 시도는 상태와 저장 데이터를 바꾸지 않아야 한다.
- FR-009: 입실 반려동물의 목록 칩에는 `호텔` 배지가 표시되어야 한다.
- FR-010: 선택한 입실 반려동물의 상세 툴바도 호텔 상태를 색상과 문구로 표시해야 한다.
- FR-011: 기존 프로필의 누락된 호텔 필드는 `false`로 정규화해야 한다.
- FR-012: 신규 반려동물은 퇴실 상태로 생성되어야 한다.
- FR-013: 이름과 호텔 변경은 기존 저장 큐와 동기화 정책을 사용해야 한다.
- FR-014: 서버는 프로필의 호텔 필드 타입과 전체 입실 개수를 검증해야 한다.

## Non-Functional Requirements

- NFR-001: 사용자 제공 이름은 HTML에 삽입할 때 이스케이프해야 한다.
- NFR-002: 이름 수정과 호텔 체크는 모바일에서도 조작할 수 있어야 한다.
- NFR-003: 기존 `user_pet_food.pets_json` 구조를 확장하고 DB 스키마는 변경하지 않아야 한다.
- NFR-004: 로그인하지 않은 사용자도 동일 기능을 사용할 수 있어야 한다.
- NFR-005: 서버 검증 실패 시 DB 쓰기를 수행하지 않아야 한다.

## Edge Cases

- 공백만 있는 이름: 저장하지 않고 안내한다.
- 80자를 초과한 이름: 클라이언트 입력 길이와 서버 검증으로 거부한다.
- 같은 이름으로 저장: 유효한 저장으로 처리하며 편집 모드를 닫는다.
- 서로 다른 반려동물의 같은 이름: 기존 등록 정책처럼 허용한다.
- 호텔 입실 5마리 상태에서 입실 중인 반려동물을 다시 체크 해제: 항상 허용한다.
- `inHotel` 필드 누락: `false`로 처리한다.
- `inHotel`이 문자열 등 잘못된 타입인 서버 요청: HTTP 400으로 거부한다.
- 서버에서 이미 잘못된 6마리 입실 데이터가 조회됨: 화면은 읽되 다음 저장 시 서버 검증으로 거부하며, 정상 UI에서는 추가 입실을 허용하지 않는다.

## Data Requirements

- 기존 프로필 필드 `id`, `name`, `type`, `preferences`, `tried`, `customFoods`, `hiddenFoodIds`를 유지한다.
- `inHotel`: 반려동물별 호텔 입실 여부를 나타내는 불리언. 신규·누락 기본값은 `false`.
- 기존 로컬 저장 키 `heartopia_pet_food_profiles`와 로그인 동기화 시 `user_pet_food.pets_json`에 함께 저장한다.
- 삭제, 마이그레이션, 동기화 병합은 기존 프로필 단위 동작을 유지한다.

## Clarifications

- Q: 호텔에는 몇 마리까지 체크할 수 있는가?
  A: 전체 등록 반려동물 중 동시에 최대 5마리다.

- Q: 여섯 번째를 체크하면 기존 입실 반려동물을 자동 퇴실시키는가?
  A: 아니다. 여섯 번째 변경을 거부하고 사용자가 기존 입실 상태를 직접 해제하게 안내한다.

- Q: 이름을 수정하면 기존 먹이 기록이 초기화되는가?
  A: 아니다. 같은 프로필의 `name`만 변경하므로 모든 기록과 상태를 유지한다.
