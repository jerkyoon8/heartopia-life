# Feature Spec: 퍼즐·모래 조각 수집 기록과 메인 진행도

## Source

- PRD: `specs/030-puzzle-sandbox-checklist-progress/prd.md`
- Principles: `specs/principles.md`

## User Scenarios

### Scenario 1: 퍼즐 보유 상태 기록

- Given 사용자가 퍼즐 도감의 카드 또는 표 보기를 열었다.
- When 특정 퍼즐의 체크 버튼을 누른다.
- Then 같은 퍼즐의 모든 보기 상태가 완료로 표시되고 기존 체크리스트 저장 정책에 따라 보존된다.

### Scenario 2: 모래 조각 보유 상태 기록

- Given 사용자가 모래 조각 도감을 열었다.
- When 특정 모래 조각의 체크 버튼을 누른다.
- Then 해당 항목이 완료로 표시되며 검색·필터·보기 전환 후에도 상태가 유지된다.

### Scenario 3: 빠진 항목 확인

- Given 사용자가 일부 퍼즐 또는 모래 조각을 완료 처리했다.
- When 수집된 항목 숨기기를 사용한다.
- Then 완료 항목은 숨겨지고 아직 없는 항목만 남는다.

### Scenario 4: 통합 수집 도감 확인

- Given 퍼즐 또는 모래 조각 체크 기록이 있다.
- When 통합 수집 도감을 연다.
- Then 두 카테고리가 탭과 목록에 나타나고 카테고리 및 전체 진행률에 반영된다.

### Scenario 5: 메인 진행도 확인

- Given 로컬 또는 계정 체크 기록이 있다.
- When 메인 페이지를 연다.
- Then 체크를 지원하는 각 카드가 `완료 / 전체`를 표시하고 비지원 카드는 기존 데이터 개수를 표시한다.

### Scenario 6: 로그인 동기화 데이터 로딩

- Given 로그인 사용자가 체크리스트 동기화를 켰다.
- When 메인 페이지 또는 신규 도감 페이지를 연다.
- Then 계정 체크리스트를 불러온 뒤 완료 상태와 진행도를 표시한다.

## Functional Requirements

- FR-001: 퍼즐의 체크 키는 `puzzle_id_{id}`여야 한다.
- FR-002: 모래 조각의 체크 키는 `sandbox_id_{id}`여야 한다.
- FR-003: 퍼즐·모래 조각 카드와 표 행은 `.sync-item`, `data-sync-key`, `.sync-check-btn` 계약을 사용해야 한다.
- FR-004: 카드와 표의 동일 항목 상태는 `ChecklistCore` 변경 알림을 통해 함께 갱신되어야 한다.
- FR-005: 신규 두 페이지는 기존 위키 필터의 수집 완료 숨김 기능을 제공해야 한다.
- FR-006: 비로그인 또는 동기화 OFF 상태에서는 `heartopia_checklist` 로컬 저장소를 사용해야 한다.
- FR-007: 동기화 ON 상태에서는 기존 `/api/user/checklist` 읽기·항목 저장·삭제 API를 사용해야 한다.
- FR-008: 통합 수집 도감은 퍼즐과 모래 조각 목록을 서버 모델로 받아 각 항목을 체크할 수 있어야 한다.
- FR-009: 통합 수집 도감의 전체·카테고리별 완료 개수와 퍼센트는 신규 두 카테고리를 포함해야 한다.
- FR-010: 메인 진행도 집계는 각 카드가 제공하는 유효 체크 키 목록을 기준으로 해야 한다.
- FR-011: 메인 진행도는 `mastery_` 보조 키와 현재 DB에 없는 오래된 키를 제외해야 한다.
- FR-012: 메인 페이지의 체크 지원 카드는 데이터 로딩 전 로딩 표시를, 로딩 후 `완료 / 전체 완료` 문구를 보여야 한다.
- FR-013: 주민·반려동물·동물·채집 등 현재 체크 기능이 없는 카드는 기존 데이터 개수 문구를 유지해야 한다.
- FR-014: 메인 페이지가 동기화 ON일 때도 체크 항목 DOM 존재 여부와 관계없이 계정 데이터를 한 번 불러와야 한다.
- FR-015: 체크 상태가 같은 탭 또는 다른 탭에서 변경되면 메인 진행도를 다시 계산해야 한다.

## Non-Functional Requirements

- NFR-001: 메인 진행도 계산을 위해 카테고리별 전체 데이터 API를 추가 호출하지 않아야 한다.
- NFR-002: 체크 키 목록은 메인 HTML에 필요한 최소 정보만 직렬화하며 개인정보를 포함하지 않아야 한다.
- NFR-003: 체크 버튼은 키보드 접근이 가능한 `button` 요소와 상태를 나타내는 접근성 속성을 사용해야 한다.
- NFR-004: 기존 체크리스트 키와 저장 데이터는 변경하거나 삭제하지 않아야 한다.
- NFR-005: DB 스키마 변경 없이 기존 `user_checklist.item_key` 저장 구조를 재사용해야 한다.

## Edge Cases

- 저장 데이터가 비어 있으면 모든 체크 지원 카드는 `0 / 전체 완료`를 표시한다.
- 계정 데이터 조회가 실패하면 메인 카드는 오류 또는 재시도 가능한 비확정 상태를 유지하며 로컬 데이터를 계정 데이터처럼 표시하지 않는다.
- 같은 항목이 카드와 표에 동시에 렌더링되어도 완료 개수는 한 번만 센다.
- DB에서 항목이 삭제되었지만 체크 키가 저장되어 있으면 완료 개수에서 제외한다.
- 신규 항목이 DB에 추가되면 전체 수만 증가하고 완료 수는 유지된다.
- 필터로 항목이 숨겨져도 카테고리 전체 진행도는 변하지 않는다.
- 체크를 해제하면 카드·표·통합 체크리스트의 상태와 메인 집계가 다음 로드 또는 동일 페이지 관찰자 갱신 시 일치한다.

## Data Requirements

- 퍼즐: DB의 `puzzle_collections.id`, 이름, 전체 개수
- 모래 조각: DB의 `sandbox_collections.id`, 이름, 전체 개수
- 기존 체크 카테고리: 현재 템플릿과 동일한 이름 기반 키 또는 바다 청소 ID 기반 키
- 저장 값: 완료는 기존 관례대로 정수 `0`; 미완료는 키 삭제
- 계정 저장: 기존 `user_checklist(user_id, item_key, star_rating)` 사용
- 삭제 정책: 사용자가 체크를 해제하면 해당 키만 삭제한다.

## Clarifications

- Q: 메인 진행도를 신규 두 카드에만 표시할지 모든 체크 지원 카드에 표시할지?
  A: 모든 체크 지원 카드에 적용하고 비지원 카드는 기존 데이터 개수를 유지한다.
- Q: 신규 기록도 로그인 계정 동기화를 지원할지?
  A: 기존 체크리스트의 일부로 취급하여 동일한 동기화 정책을 적용한다.
