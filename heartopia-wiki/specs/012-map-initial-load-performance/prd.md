# PRD: 지도 초기 로딩 성능 개선

## 1. Summary

### Problem

인터랙티브 지도는 지도 이미지 로딩이 끝난 뒤 핀·구역 API를 호출하고, 그 응답 뒤에 다시 도감 API 6개를 호출한다. 특히 고래낙하 협곡은 실제로 사용하지 않는 물고기·곤충·새·주민 데이터까지 받아 초기 화면이 불필요하게 늦어진다.

### Proposed Solution

지도 이미지와 초기 API 요청을 동시에 시작하고, 활성 지도에서 지원하는 도감 종류만 요청한다. 핀·도감 데이터가 준비된 뒤 사이드 목록을 한 번만 초기 렌더링하되 기존 지도 표시와 관리자 편집 동작은 유지한다.

### Success Criteria

- 지도 이미지와 초기 데이터 요청 사이의 직렬 의존성이 제거된다.
- 고래낙하 협곡 초기 진입 시 도감 API 요청이 6개에서 2개(채집물·동물)로 줄어든다.
- 초기 사이드 목록 전체 렌더링이 2회에서 1회로 줄어든다.
- 기본 지도에서 처음부터 숨김 상태인 핀은 Leaflet 레이어에 붙였다가 제거하지 않는다.
- 기본 지도 해상도 `1995 × 1998`을 유지하면서 서비스 이미지 용량을 1MB 미만으로 줄인다.
- 기본 지도와 고래낙하 협곡의 기존 핀·카테고리·구역 기본 표시 정책이 유지된다.

## 2. Users And Use Cases

### Primary Users

- 인터랙티브 지도에서 위치를 탐색하는 일반 사용자
- 지도 핀과 구역을 관리하는 관리자

### User Stories

- As a 지도 사용자, I want to 지도가 더 빨리 준비되길 원한다, so that 위치 정보를 기다림 없이 탐색할 수 있다.
- As a 관리자, I want to 기존 편집 기능이 유지되길 원한다, so that 성능 개선 뒤에도 핀과 구역을 계속 관리할 수 있다.

## 3. Functional Scope

### In Scope

- 이미지와 초기 지도 데이터의 병렬 요청
- 지도별 도감 API 요청 범위 정의
- 초기 카테고리 목록 중복 렌더링 제거
- 초기 숨김 핀의 불필요한 DOM 부착 방지
- 기본 지도 PNG 원본을 유지하고 서비스 경로를 고품질 WebP로 전환
- 로딩 실패 로그 정리
- 지도 초기화 계약을 확인하는 자동 테스트

### Out Of Scope

- 지도 이미지 해상도 변경
- API 응답 캐시 정책 변경
- Leaflet 교체, 마커 클러스터링, 캔버스 렌더러 도입
- 기존 전체 표시 정책이나 지도 UI 디자인 변경
- 운영 서버 배포 및 실사용자 성능 측정

## 4. Acceptance Criteria

- 페이지 진입 시 이미지 다운로드 완료를 기다리지 않고 핀·구역·필요 도감 요청이 시작된다.
- 기본 지도는 기존처럼 채집물·물고기·새·곤충·동물·주민 도감을 요청한다.
- 고래낙하 협곡은 채집물·동물 도감만 요청하며 나머지 마스터 배열은 빈 배열로 유지한다.
- 모든 초기 데이터가 준비되면 마커, 사이드 목록, 딥 링크, 구역 라벨이 기존 순서와 기능을 유지하며 초기화된다.
- 초기 데이터 요청 실패 시 오류가 콘솔에 남고 잘못된 부분 초기화를 진행하지 않는다.
- 관리자 핀 추가·삭제 및 구역 위치 저장 로직은 변경하지 않는다.

## 5. Constraints

- Tech: Spring Boot, Thymeleaf, Vanilla JavaScript, Leaflet 1.9.4
- Time: 초기 로딩 경로의 최소 변경으로 제한
- Data: 기존 API 응답 형식과 `mapKey` 계약 유지
- External Dependencies: 새 의존성 없음

## 6. Risks

- 한 API 실패가 전체 초기화를 막을 수 있음: 현재 필수 초기 데이터 계약을 유지하고 단일 오류 경로에서 원인을 기록한다.
- 향후 두 번째 지도에 새 카테고리가 추가될 때 요청 설정 누락 가능: 지도 설정에 지원 카테고리를 명시하고 테스트로 고정한다.
- 병렬 요청으로 서버 순간 동시 요청 수가 늘 수 있음: 두 번째 지도는 총 요청 수 자체를 줄이고, 기본 지도도 기존 총량 안에서 시작 시점만 겹치게 한다.
