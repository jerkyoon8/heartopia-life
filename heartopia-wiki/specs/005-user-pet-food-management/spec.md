# Feature Spec: 사용자별 반려동물 먹이 관리

## Source

- PRD: `specs/005-user-pet-food-management/prd.md`
- Principles: `specs/principles.md`

## User Scenarios

### Scenario 1: 사용자 정의 먹이 추가

- Given 사용자가 등록된 반려동물을 선택했다.
- When 중복되지 않은 먹이 이름을 입력하고 추가한다.
- Then 해당 반려동물의 목록에만 사용자 정의 먹이가 나타나고 저장된다.

### Scenario 2: 기본 먹이 삭제

- Given 사용자가 기본 먹이가 표시된 반려동물을 선택했다.
- When 기본 먹이의 삭제 버튼을 누르고 확인한다.
- Then 해당 먹이는 현재 반려동물에서만 숨겨지고 공통 기본 목록은 바뀌지 않는다.

### Scenario 3: 사용자 정의 먹이 삭제

- Given 사용자가 직접 추가한 먹이가 있다.
- When 해당 먹이를 삭제한다.
- Then 먹이 항목과 그 먹이의 먹여봄·선호도 기록이 현재 반려동물 프로필에서 제거된다.

### Scenario 4: 기본 먹이 복원

- Given 사용자가 기본 먹이를 삭제해 숨겼다.
- When 같은 이름을 사용자 정의 먹이 추가 폼에 입력한다.
- Then 숨김 상태가 해제되어 원래 기본 먹이가 다시 나타난다.

### Scenario 5: 비로그인 로컬 관리

- Given 사용자가 로그인하지 않았다.
- When 먹이를 추가하거나 기본 먹이를 삭제한다.
- Then 변경 결과는 로그인·비로그인이 함께 쓰는 현재 브라우저 저장 키에 저장된다.

### Scenario 6: 기존 DB 먹이 이미지 재사용

- Given 사용자가 기존 물고기·요리·채집·작물 DB에 있는 이름으로 먹이를 직접 추가한다.
- When 먹이 카드가 표시된다.
- Then 공백 차이를 무시하고 일치한 DB 항목의 이미지 URL을 사용한다.

## Functional Requirements

- FR-001: 시스템은 로그인 여부와 사용자 ID를 페이지 스크립트에 제공해야 한다.
- FR-002: 시스템은 선택된 반려동물 프로필에 사용자 정의 먹이 배열을 저장해야 한다.
- FR-003: 시스템은 선택된 반려동물 프로필에 숨긴 기본 먹이 ID 배열을 저장해야 한다.
- FR-004: 시스템은 기본 먹이에서 숨긴 ID를 제외한 뒤 사용자 정의 먹이를 합쳐 표시해야 한다.
- FR-005: 시스템은 공백을 정리한 먹이 이름만 등록하고 빈 이름을 거부해야 한다.
- FR-006: 시스템은 공백과 대소문자 차이를 제거한 이름 기준으로 표시 중인 먹이의 중복 등록을 거부해야 한다.
- FR-007: 시스템은 숨긴 기본 먹이와 같은 이름이 입력되면 해당 기본 먹이를 복원해야 한다.
- FR-008: 시스템은 로그인 여부와 관계없이 먹이 추가·삭제 컨트롤과 동작을 허용해야 한다.
- FR-009: 시스템은 기본 먹이 삭제 시 사용자 프로필에 숨김 ID만 기록해야 한다.
- FR-010: 시스템은 사용자 정의 먹이 삭제 시 배열 항목과 관련 상태를 제거해야 한다.
- FR-011: 시스템은 기존 프로필에 신규 필드가 없어도 빈 배열로 정규화해야 한다.
- FR-012: 시스템은 사용자 정의 먹이도 검색, 필터, 먹여봄, 좋아요, 싫어요 기능에 포함해야 한다.
- FR-013: 시스템은 서버 저장·마이그레이션·동기화 요청의 프로필 JSON 구조를 검증해야 한다.
- FR-014: 시스템은 반려동물 20마리, 사용자 정의 먹이 100개, 숨김 먹이 200개, 먹여봄·선호도 상태 각각 300개를 최대값으로 제한해야 한다.
- FR-015: 시스템은 반려동물 이름과 사용자 정의 먹이 이름을 1자 이상 80자 이하로 제한해야 한다.
- FR-016: 시스템은 잘못된 펫 종류, 선호도 값, 불리언이 아닌 먹여봄 값, 중복 사용자 정의 먹이를 거부해야 한다.
- FR-017: 시스템은 동기화가 꺼진 로그인·비로그인 상태에서 같은 `heartopia_pet_food_profiles` 키를 사용해야 한다.
- FR-018: 시스템은 사용자 정의 먹이 이름을 기존 물고기·요리·채집·작물 DB 이름과 공백을 제외해 비교하고 일치하면 DB 이미지 URL을 표시해야 한다.

## Non-Functional Requirements

- NFR-001: 다른 사용자의 프로필 JSON을 조회하거나 변경할 수 없어야 한다.
- NFR-002: 먹이 이름을 HTML로 표시할 때 이스케이프해 스크립트 삽입을 막아야 한다.
- NFR-003: 기존 저장 데이터와 DB 스키마를 변경하지 않고 하위 호환되어야 한다.
- NFR-004: 모바일 화면에서도 추가 폼과 삭제 버튼을 사용할 수 있어야 한다.
- NFR-005: 연속 저장은 요청 순서가 보장되어 마지막 화면 상태가 서버에 남아야 한다.
- NFR-006: 검증 실패 요청은 HTTP 400과 사용자에게 노출 가능한 오류 메시지를 반환하고 DB 쓰기를 수행하지 않아야 한다.
- NFR-007: 로컬 데이터는 로그인 상태가 바뀌어도 이어지도록 하나의 localStorage 키를 사용해야 한다.
- NFR-008: DB 이미지 목록 조회는 기존 서비스 캐시를 사용하고 외부 API를 호출하지 않아야 한다.

## Edge Cases

- 앞뒤 공백만 있는 이름: 등록하지 않고 안내 문구를 표시한다.
- 표시 중인 기본/사용자 정의 먹이와 같은 이름: 중복 등록하지 않는다.
- 숨긴 기본 먹이와 같은 이름: 기본 먹이를 복원한다.
- 사용자 정의 먹이 ID 충돌: 시간·난수를 포함한 `custom-food-` 접두사 ID를 사용한다.
- 선택된 반려동물이 없음: 추가 폼을 비활성화하고 안내한다.
- 비로그인 상태의 추가·삭제: 로그인 로컬 기록과 같은 localStorage 키에 저장한다.
- DB 이름은 일치하지만 이미지 URL이 비어 있음: 기존 대체 아이콘을 표시한다.
- 먹이 삭제 후 현재 필터 결과가 비어 있음: 기존 빈 검색 결과 문구를 표시한다.
- 오래된 프로필의 잘못된 신규 필드 타입: 빈 배열로 정규화한다.
- 서버 요청의 신규 필드 타입이 잘못됨: HTTP 400으로 거부한다.
- 사용자 정의 먹이 이름이 80자를 초과하거나 개수가 100개를 초과함: HTTP 400으로 거부한다.

## Data Requirements

- 반려동물 프로필의 기존 필드 `id`, `name`, `type`, `preferences`, `tried`를 유지한다.
- `customFoods`: `{ id, name }` 객체 배열. 해당 반려동물에만 속한다.
- `hiddenFoodIds`: 기본 먹이 ID 문자열 배열. 해당 반려동물에만 속한다.
- 동기화 활성화 시 기존 `user_pet_food.pets_json`에 함께 저장한다.
- 동기화 비활성 로그인 사용자와 비로그인 사용자는 모두 `heartopia_pet_food_profiles` 키를 사용한다.
- DB 이미지 매핑은 프로필 JSON에 저장하지 않고 화면 렌더링 시 최신 도감 데이터로 계산한다.

## Clarifications

- Q: 기본 먹이 삭제가 다른 사용자와 반려동물에도 적용되는가?
  A: 아니다. 현재 사용자의 현재 반려동물 프로필에서만 숨긴다.
- Q: 사용자 정의 먹이는 누가 볼 수 있는가?
  A: 비로그인 데이터는 해당 브라우저 사용자만, 로그인 데이터는 해당 계정 사용자만 볼 수 있다.
- Q: 비로그인과 로그인 사용자가 같은 localStorage를 사용하는가?
  A: 그렇다. 동기화가 꺼져 있으면 로그인 여부와 관계없이 같은 키를 사용한다.
- Q: 기본 먹이를 영구적으로 공통 데이터에서 제거하는가?
  A: 아니다. 개인별 숨김 처리하며 같은 이름을 다시 추가하면 복원한다.
- Q: 사용자 정의 먹이에 이미지를 등록하는가?
  A: 사용자가 이미지를 직접 등록하지는 않는다. 기존 먹이 DB 이름과 일치하면 그 이미지를 재사용하고, 일치하지 않으면 대체 아이콘을 사용한다.
