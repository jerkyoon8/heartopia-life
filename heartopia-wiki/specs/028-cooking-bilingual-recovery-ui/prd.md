# PRD: 요리 회복량 UI·영문명 참고표

## 1. Summary

### Problem

현재 요리 목록과 상세 화면에는 등급별 회복량을 저장하거나 보여줄 구조가 없다. 영문명은 서비스 데이터가 아니라 검증용 비교 자료로만 관리해야 한다.

### Proposed Solution

요리 데이터에는 1~5성 회복량만 추가하고 가격 영역 아래 별도 UI로 표시한다. 한글·영문 이름 비교표는 DB/UI 밖의 Markdown 자료로 유지한다.

### Success Criteria

- 기존 Heartodex 175개 한글·영문 매칭이 Markdown 참고표로 보존된다.
- 출처에서 숫자가 확인된 111개 요리의 1~5성 회복량이 저장·표시된다.
- 회복량이 공개되지 않은 요리는 값을 추정하지 않고 `정보 없음`으로 표시한다.
- 기존 목록/상세 URL, 필터, 체크리스트 키와 가격 UI가 그대로 동작한다.

## 2. Users And Use Cases

### Primary Users

- 게임 내 한글·영문 요리명을 대조하거나 별 등급별 회복량을 확인하는 위키 방문자
- 요리 데이터를 관리하는 관리자

### User Stories

- 방문자로서 별 등급별 회복량을 가격과 함께 확인하고 싶다.
- 방문자로서 요리 카드와 상세 화면에서 별 등급별 회복량을 바로 확인하고 싶다.
- 관리자로서 새 요리나 수정된 요리의 회복량을 관리하고 싶다.

## 3. Functional Scope

### In Scope

- `cooking_collections` 회복량 컬럼과 검증 데이터 백필
- Java 모델/MyBatis 조회·관리자 CRUD 연결
- 한글·영문 175개 비교용 Markdown 생성
- 요리 카드와 상세 화면 가격 하단의 1~5성 회복량 UI
- 회복량 조회·관리자 수정 회귀 테스트

### Out Of Scope

- 출처에 없는 64개 요리의 회복량 추정
- 기존 가격 불일치의 운영 DB 자동 수정
- 배포, 운영 DB SQL 실행, 커밋 또는 push

## 4. Acceptance Criteria

- 서비스 DB, 모델, Mapper, 관리자 폼과 공개 UI에 영문명을 추가하지 않는다.
- 카드 하단과 상세 가격 하단에 1~5성 회복량이 같은 순서로 표시된다.
- 일부 또는 전체 회복량이 NULL이어도 페이지 렌더링이 실패하지 않는다.
- 관리자 추가/수정 화면에서 회복량을 입력할 수 있다.
- SQL 적용 전 기존 운영 코드에는 영향을 주지 않으며, SQL과 코드는 push하지 않는다.

## 5. Constraints

- Tech: Java 17, Spring Boot, Thymeleaf, MyBatis, MySQL 8.0
- Data: 영문명 175개는 외부 참고표 전용이며 숫자 회복량 111개만 DB 백필됨
- Deployment: 스키마/백필 SQL을 코드보다 먼저 적용해야 한다.
- Safety: 운영 서버와 운영 DB를 변경하지 않으며 `git push`를 실행하지 않는다.

## 6. Risks

- 핫패스 SELECT가 새 컬럼에 의존함: SQL 선적용 순서를 문서화하고 테스트로 컬럼 연결을 검증한다.
- 미공개 회복량을 사실처럼 보일 위험: NULL을 유지하고 `정보 없음`으로 명시한다.

## 7. Open Questions

- 없음. 이번 구현은 검증된 값만 채우고 미공개 값은 NULL로 유지한다.
